# Documentation Maintenance Rules for Codex

The following section is intended to help Codex keep this document aligned with the implementation.

## Source of Truth

The implementation on the CreatorInc repository's `main` branch is the source of truth for what the app actually uses.

Do not document planned or speculative functionality as implemented.

## Database Evidence Source

Read the database setup from the [`main` branch of `superbase-db-queries`](https://github.com/den504/superbase-db-queries/tree/main) as a read-only evidence source.

Use it to verify relevant:

- Tables, columns, keys, and relationships.
- Migrations and setup scripts.
- Row Level Security policies.
- Database functions and triggers.
- Queries used by CreatorInc.

CreatorInc's current `main`-branch integration remains the authority for which database behaviour is implemented and used by the app. Clearly label database work that is incomplete, planned, unused, or not referenced by CreatorInc. If the database repository cannot be accessed, do not infer its contents; document only what can be verified locally and record the access problem.

## When Code Changes

When source code changes, inspect whether the change affects:

- Chapter 3 — System Requirements.
- Chapter 4 — System Design.
- Chapter 5 — Implementation.
- Chapter 6 — Testing.
- Chapter 7 — Review of Requirements.
- Appendix B — Program Code.

Update only affected sections.


## Implementation Documentation

When a significant class, service, model, ViewModel, View, database table, API integration, or algorithm is added or changed, update the relevant subsection in **Chapter 5.6 Overview of Software Components**.

Include:

- Purpose.
- Responsibilities.

- Requirements implemented.

## Design vs Implementation

Do not silently overwrite the original design when implementation changes.

Where Chapter 4 describes the intended design and Chapter 5 describes the final implementation, record meaningful differences in Chapter 5.

## Testing

When tests are added or changed:

- Add the appropriate test record.
- Associate tests with requirements where possible.
- Record actual outcomes.
- Do not mark tests as passed unless evidence exists in the codebase or test results.

## Documentation Accuracy

Never:

- Invent functionality.
- Invent test results.
- Invent performance figures.
- Invent survey results.
- Invent academic references.
- Invent user feedback.
- Invent implementation problems.

Use placeholders such as `[TO COMPLETE]` where the repository does not contain enough evidence.
